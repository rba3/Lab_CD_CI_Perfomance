PokeAPI Perf Lab · Prácticas con JMeter

Pruebas de rendimiento con Apache JMeter contra la PokeAPI, orquestadas por GitHub Actions y validadas por un agente de IA. Este es el manual de prácticas del equipo colaborador.

Qué es este laboratorio

Medir, analizar y mejorar el rendimiento en cada corrida

El laboratorio ejecuta planes de JMeter (smoke y load) contra endpoints de la PokeAPI, extrae métricas (p50, p95, p99, throughput, % de error), un agente de IA emite un veredicto PASS / WARN / FAIL en español y el resultado se publica como reporte con gráficas. Todo corre en GitHub Actions, sin infraestructura propia.

Motor de carga

Apache JMeter 5.6.3 con planes parametrizados y Response Assertions (HTTP 200 + cuerpo JSON).

Orquestación

GitHub Actions por cron diario y ejecución manual, con caché de JMeter y permisos mínimos.

Validación con IA

Agente de GitHub Models que analiza las métricas contra los SLOs y da veredicto con recomendaciones.

Antes de empezar

Preparación del entorno

Para la mayoría de las prácticas basta con GitHub (ejecutar el workflow y leer el reporte). Para las prácticas locales necesitas Apache JMeter y Python 3 instalados.

# 1. Clonar el repositorio
git clone https://github.com/rba3/Lab_CD_CI_Perfomance.git
cd Lab_CD_CI_Perfomance

# 2. Correr un smoke local (requiere JMeter en el PATH)
jmeter -n -t tests/smoke.jmx -Jendpoints=config/pokeapi-endpoints.csv \
  -l results/smoke.jtl -e -o reports/html-smoke

# 3. Generar métricas y reporte
python3 scripts/parse_results.py results/smoke.jtl smoke reports/metrics-smoke.json
python3 scripts/gen_report.py --out reports/report-local.md --date "local" \
  --metrics reports/metrics-smoke.json

Regla de convivencia: la PokeAPI es pública. Trabaja siempre con carga moderada y con think time. No subas los umbrales de load sin acordarlo con el equipo.

Manual del colaborador

Prácticas de performance con JMeter

Ocho prácticas progresivas, de lo básico a lo avanzado. Cada una tiene un objetivo, los pasos y un criterio de éxito claro. Trabaja en una rama y abre un Pull Request con tu evidencia.

1

Primera corrida y lectura de métricas

Básico

Objetivo: ejecutar el laboratorio y entender qué significan las métricas.

  1. En GitHub, entra a Actions → Performance PokeAPI (JMeter) → Run workflow con scenario = smoke.
  2. Cuando termine, abre el reporte generado en reports/ y la sección "Último reporte" del README.
  3. Identifica y define con tus palabras: p50, p95, p99, throughput y % de error.

Criterio de éxito: puedes explicar la diferencia entre p95 y promedio, y decir qué endpoint fue el más lento en tu corrida.

2

Agregar un endpoint al plan

Básico

Objetivo: extender la cobertura sin tocar el .jmx.

  1. Edita config/pokeapi-endpoints.csv y agrega una fila label,path (por ejemplo item,/api/v2/item/1).
  2. Corre un smoke y confirma que el nuevo endpoint aparece como sampler propio en las métricas.

Criterio de éxito: el reporte muestra métricas separadas para tu endpoint nuevo.

Pista: el nombre del sampler usa ${label}, por eso cada fila del CSV se agrupa por separado.

3

Parametrizar la carga

Intermedio

Objetivo: observar cómo cambia la latencia al variar la concurrencia.

  1. Lanza el workflow manual con scenario = load y ajusta threads, rampup, duration y think.
  2. Corre al menos dos configuraciones distintas y anota el p95 de cada una.
  3. Explica por qué sube o baja el p95 al cambiar los hilos o el think time.

Criterio de éxito: una mini tabla comparando 2+ corridas (threads vs p95 vs throughput) con tu conclusión.

Recuerda la regla de convivencia: nada de cargas agresivas contra la API pública.

4

Endurecer las validaciones

Intermedio

Objetivo: hacer que la prueba falle cuando la respuesta no es la esperada, no solo por HTTP 200.

  1. En el plan .jmx, agrega o ajusta una Response Assertion para validar un campo del JSON (por ejemplo que el cuerpo contenga "name").
  2. Corre un smoke y confirma que sigue en verde con la validación más estricta.
  3. Provoca temporalmente un fallo (por ejemplo apuntando a un path inválido) para ver la aserción marcar error.

Criterio de éxito: demuestras una corrida en verde con la validación fuerte y una en rojo cuando la respuesta no cumple.

5

El gate de Pull Request

Intermedio

Objetivo: entender cómo el performance protege la rama principal.

  1. Crea una rama, haz un cambio pequeño y abre un Pull Request hacia main.
  2. Observa que el check perf corre solo el escenario smoke.
  3. Explica por qué en un PR el workflow no commitea el reporte ni abre issues.

Criterio de éxito: tu PR muestra el check perf en verde y explicas la diferencia con la corrida por cron.

Disponible en el repositorio con cierre de ciclo (rba3/Lab_CD_CI_Perfomance).

6

Cierre de ciclo: issue automático

Avanzado

Objetivo: ver el flujo DevOps completo cuando el rendimiento se degrada.

  1. Lanza el workflow manual con el input simular_fallo = WARN (o FAIL).
  2. Verifica que se abre un issue automático con label performance, las métricas y el análisis del agente de IA.
  3. Lee el análisis del agente y propón, en un comentario del issue, qué revisarías primero.

Criterio de éxito: existe un issue generado por la corrida y tu comentario con un plan de diagnóstico.

Disponible en el repositorio con cierre de ciclo (rba3/Lab_CD_CI_Perfomance). El input simular_fallo existe porque la PokeAPI casi siempre da PASS.

7

Ajustar los SLOs

Avanzado

Objetivo: calibrar cuándo el laboratorio debe alertar.

  1. Revisa los umbrales de PASS / WARN / FAIL (paso "Armar prompt para el agente" y el fallback por umbrales del workflow).
  2. Propón un cambio justificado (por ejemplo bajar el p95 de FAIL) y documéntalo.
  3. Demuestra con una corrida que el nuevo umbral cambia el veredicto como esperabas.

Criterio de éxito: un PR que cambia un umbral, con la evidencia de la corrida antes y después.

8

Reto: diseña tu propio plan

Avanzado

Objetivo: aplicar todo lo aprendido creando un escenario nuevo.

  1. Crea un plan .jmx nuevo (por ejemplo un spike test con subida rápida de hilos) reutilizando el CSV de endpoints.
  2. Intégralo como opción del workflow y documenta cómo correrlo.
  3. Entrega un breve reporte con tus hallazgos: qué observaste y qué recomendarías.

Criterio de éxito: un plan ejecutable en el laboratorio y un reporte con conclusiones defendibles.

Marco normativo

Visión de línea base

La línea base es la corrida de referencia contra la que se comparan las siguientes: si una medición nueva se desvía de forma significativa, es un hallazgo. El laboratorio fundamenta esa línea base en estándares ISO/IEC e ISTQB.

Línea base (baseline): conjunto de valores de rendimiento medidos y acordados como referencia formal. Toda corrida posterior se evalúa contra ella para detectar mejoras o regresiones. ISO/IEC/IEEE 24765 · vocabulario
ISO/IEC 25010

Modelo de calidad

Qué medimos: la característica Eficiencia de desempeño — comportamiento temporal, utilización de recursos y capacidad.

ISO/IEC 25023

Medidas de calidad

Cómo lo medimos: tiempo de respuesta (p50 / p95 / p99), throughput y % de error. Son las métricas del reporte.

ISO/IEC 25040

Proceso de evaluación

Cómo evaluamos: requisitos → especificación → diseño → ejecución → conclusión. El pipeline lo automatiza.

ISO/IEC/IEEE 29119

Proceso de pruebas

Cómo lo documentamos: planeación, diseño, ejecución y reporte. Los planes .jmx y el reporte son los artefactos.

ISO/IEC/IEEE 24765

Vocabulario común

Lenguaje compartido: línea base, prueba de rendimiento, defecto, criterio de aceptación.

ISTQB

Método

La prueba de rendimiento es no funcional; la línea base es el criterio de comparación, con criterios de entrada y salida definidos.

Escalabilidad entre ambientes

Proyectar de QA a producción con la USL

Cuando QA y producción no están homologados (prod tiene más CPU y RAM), no basta con extrapolar linealmente. La Ley Universal de Escalabilidad (USL, Neil Gunther) modela cómo escala realmente el throughput al agregar recursos, y permite proyectar prod a partir de mediciones en QA.

C(N) = N / ( 1 + α(N−1) + β·N(N−1) )
C(N): capacidad relativa (throughput) con N unidades  ·  N: nodos, vCPUs o concurrencia
α Contención
Parte serializada que no paraleliza (locks, recurso único). Aplana la curva.
β Coherencia
Costo de coordinar nodos (sincronización, red). Con β>0 el rendimiento se degrada tras el pico.
N* Punto óptimo
N* = √((1−α)/β). Más allá de N*, agregar recursos empeora el throughput.

Cómo aplicarla cuando QA ≠ prod

  1. Barrido en QA. Corre load variando N (por ejemplo 5, 10, 20, 40, 80 usuarios o vCPUs) y registra el throughput X(N) de cada punto. Mínimo 5–6 puntos.
  2. Ajusta la curva. Haz una regresión USL sobre esos puntos para obtener α y β. La forma de la curva describe el software y la arquitectura, no el hardware: por eso α y β se conservan entre ambientes.
  3. Homologa la base. Mide la capacidad de un nodo o core en cada ambiente con un micro-benchmark de 1 hilo: obtienes C1QA y C1prod. El factor de hardware es C1prod / C1QA.
  4. Proyecta prod. Aplica X_prod(N) ≈ C1_prod × C(N): escalas la capacidad base al hardware de prod y usas la misma curva (α, β) medida en QA. Así estimas throughput, N óptimo y punto de saturación de prod sin tenerlo homologado.

Entregable: α, β y N* estimados, más la curva proyectada de prod con su throughput máximo.

Límite del modelo (principio ISTQB: probar depende del contexto): la USL asume nodos homogéneos y misma arquitectura de software. Si prod cambia topología (réplicas de BD, caché, red), α y β pueden cambiar. Valida siempre con al menos un punto real en prod antes de dar la proyección por firme.
